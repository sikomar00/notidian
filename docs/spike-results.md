# 시험(Spike) 결과 (2026-11-13, 일부 완료)

방법은 [spike-guide](./spike-guide.md), 기준은 [Spec 8절](./04-spec.md)을 본다. 실패하면 구현을 멈추고 대안을 사용자에게 묻는다.

**측정 환경: Ego Lite(Chromium 156)에서 확장을 올려 측정했다. 요구 환경인 실제 Chrome 결과가 아니다.** 시험용 Notion 데이터는 `시험용 상위 페이지` 아래에만 만들었고, 읽기 전용 통합 토큰으로 읽었다. 결과 기록에는 토큰·제목·본문을 쓰지 않는다.

## 시험 데이터 정답표 (`시험용 상위 페이지` 아래)
- 페이지: 연결한 루트 1 + A·B·C·D(루트 아래) + E(B 아래) / 데이터베이스 2개(`대상`: T1·T2, `항목`: I1·I2·I3, `관련`은 `대상`으로 가는 relation)
- 연결(방향): A→B(@언급), A→C(본문 링크), A→I1(@언급, 데이터베이스 항목), A→D(@언급, 토글 안에 중첩), B→A(@언급), B→C(본문 링크), C→데이터베이스 `항목`(본문 링크, 대상이 페이지가 아님), I1→T1, I2→T1, I2→T2(relation)
- 합친 뒤: A↔B(양쪽 화살표) 1선 + A–C, A–I1, A–D, B–C, I1–T1, I2–T1, I2–T2 = **페이지끼리 8선**, 데이터베이스로 가는 C의 링크는 점이 되지 않는다
- 계층(부모가 페이지): 루트→A·B·C·D, B→E. 데이터베이스 항목의 부모는 데이터 소스라 계층 선이 없다
- 시험에서 D의 본문 한 줄 추가와 제목 변경(`D (이름 변경)`)을 했다. "페이지로 연결" 블록(`link_to_page`)과 읽을 수 없는 페이지는 만들지 못해 **테스트 코드로만** 확인한다

## 이번에 알게 된 것 (Spec·PRD에 반영할 후보 — 승인 전 문서는 그대로)
1. **데이터베이스를 가리키는 링크**: 페이지로 읽으면 400 `validation_error`다. 지금 Spec은 400을 "읽을 수 없는 페이지"(회색 점)로 처리하는데, 데이터베이스 링크는 읽을 수 없는 페이지가 아니라 **페이지가 아닌 대상**이다. 회색 점을 만들지 않고 그 연결을 그래프에서 뺀다. (F-5와 Spec 5절 오류 표 수정)
2. **수정 시각이 분 단위로 내림**된다: 마지막으로 읽은 같은 분 안에 고친 내용은 다음 "다시 색인"에서 놓칠 수 있다. 수정 시각이 읽은 시각에서 2분 이내인 페이지는 다음 색인에서 한 번 더 읽는다. (Spec 5절 추가)
3. **검색 색인 지연**: 방금 만든 페이지 1개가 첫 검색에서 빠졌고(10개) 15초 뒤 나왔다(11개). "다시 색인" 직후의 아주 최근 변경은 늦게 보일 수 있다고 안내한다.
4. **수정 시각을 바꾸지 않는 경우**: 참조받는 페이지의 이름 변경은 참조하는 쪽을 바꾸지 않는다. 설계상 제목은 그 페이지 자신의 값이라 문제없다. 토글 안 중첩 블록 수정이 페이지 시각을 바꾸는지는 시험하지 못했다.
5. 실제 저장된 Notion 주소는 `app.notion.com/p/<id32>` 한 가지였고 `?p=`·슬러그 형태는 보이지 않았다. 현재 `urlToPageId`(`app.notion.com`, `notion.so`, `www.notion.so`)로 충분하다.

- S-1: 실제 Chrome에서 한 번 더.
- S-3: 내 실제 계정(또는 큰 범위)에서 평균 요청 수.
