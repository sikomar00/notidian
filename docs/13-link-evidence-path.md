# 13. 왜 연결됐나(연결 근거)와 경로 찾기 (승인 2026-11-14)

외부 리뷰와 사용성 과제 T3("두 페이지가 왜 연결됐는지 말하기", [12](./12-usability-tasks.md))에서 나온 P1 작업. 범위가 작아 문제·화면·요구·설계를 이 문서 하나에 모았다.

## 1. 문제
그래프와 받은·보낸 연결 목록은 "A가 B를 가리킨다"만 보여 준다. @언급인지 relation인지, 어떤 문장에서 가리키는지가 없어 연결을 이해하려면 노션을 열어 찾아야 한다. 처음 설계에서 연결 종류는 화면에서 구분하지 않아 저장하지 않았다([04 Spec](./04-spec.md) 3절). 두 페이지가 어떤 길로 이어지는지도 알 수 없다.

## 2. 정한 것 (2026-11-14 인터뷰)
| 질문 | 결정 |
|---|---|
| 무엇을 | 연결마다 **종류와 근거**: `@언급 · "…지난주 [로드맵] 회의에서…"`, relation이면 `relation · 속성 "관련 프로젝트"`. 근거 문장은 처음 나온 곳 하나, 앞뒤 약 30자. 종류가 섞이면 모두 적는다 |
| 어디에 | 상세 패널(좁으면 서랍)의 받은·보낸 연결 각 줄 아래 작은 글씨. 그래프 선 위 표시는 하지 않는다 |
| 선 모양 | 종류별로 바꾸지 않는다(점선은 하위 페이지 선이 쓴다) |
| 경로 찾기 | 넣는다. 패널의 "다른 페이지까지 경로" 검색칸 → `A → B → C`와 단계별 연결 종류, 그래프에서 그 길 강조. 방향 무시, 6단계까지 |
| 성공 기준 | T3을 2분 안에, 경로를 1분 안에. Notion 요청 수 그대로. 근거 때문에 늘어나는 저장은 본문 저장량의 10% 이하 |

## 4. 설계
- **근거 뽑기(`src/notion/linkEvidence.ts`, 새):** 블록과 속성에서 대상마다 `{ kinds, property?, before?, match?, after? }`. 리치텍스트 배열을 한 줄로 이어 붙여 연결이 걸린 조각의 위치에서 앞뒤 글자를 자른다(`contextAt` 재사용). 연결 대상 판정은 `extractLinks.ts`와 같은 규칙을 함께 쓴다(`richTextTargets`로 꺼냄). 연결 집합 자체(어떤 대상인지)는 지금 `extractLinks` 결과 그대로라 그래프가 바뀌지 않는다.
- **저장:** `links` 저장소의 한 줄에 `evidence?` 필드를 더한다(저장소 버전은 그대로 2). `replaceLinks(from, targets, evidence)`. 페이지 기록의 받아 둔 속성(`prefetched`)에도 속성 근거를 함께 둔다.
- **다시 읽기:** `TEXT_VERSION` 1 → 2. 상태 줄 문구는 "본문과 연결 근거를 처음 모으느라 이번엔 전체를 다시 읽어요"로.
- **화면:** `linksPanel.ts`가 줄마다 근거를 그린다(`mentionSnippet` 재사용). 근거는 `rawLinks`에서 `from→to` 열쇠로 찾는다. 양방향이면 각 방향의 근거를 따로 쓴다.
- **경로(`src/graph/path.ts`, 새):** 너비 우선 탐색. 화면은 `pathPanel.ts`(새)가 경로 검색칸(제목 검색과 같은 `setupSearch`)과 결과를 맡고, 그래프는 `setPath(ids)`로 길의 점·선을 강조한다.
- **한계(`shortcut:`):** relation이 25개를 넘어 따로 읽은 대상은 속성 이름 없이 "relation"만 표시한다.

## 5. 확인 계획
- 단위: 근거 뽑기(종류별·속성 이름·앞뒤 글자·여러 종류·@언급의 링크 주소는 링크로 세지 않음), 경로(최단·방향 무시·하위 페이지 선 제외·6단계·없음), 색인 요청 수 그대로, 버전 2로 한 번 다시 읽기.
- 자동 화면 점검(예시 데이터에 근거 넣기): 패널 근거 문구, 경로 찾기 결과·강조, 360px.
- 사람: 사용성 과제 T3·경로 찾기를 실제 데이터로.
